## 按流程找代码

### 用户上传文件后，内容怎么变得可搜索？

`documents.controller` → `chunk-upload.service` 接收/合并分片 → `documents.service` 保存原件、版本和任务 → `task-queue.runtime` 投递 → `indexing.service` 执行 → `document.parser` 提取文字 → `recursive.chunker` 切块 → `embeddings` 向量化 → `vector-store` 写入 → 新索引发布。

### 用户问问题后，答案怎么生成？

`chat.controller` 接收并校验会话 → `chat.service` → `rag.service.prepare` 选择范围、规划问题、检索及组织证据 → `llm.service` 生成 → `citations` 清理无效引用 → `history.service` 保存回答。SSE 由 `chat.controller` 发送到前端。

### 为什么全文概览会变成后台任务？

`rag.service` 判断全文证据放不进模型上下文 → `qa-tasks.service` 保存证据快照并受理任务 → Worker 调用 `summary.service` 分组摘要、合并并核查原文 → 保存消息及任务覆盖情况 → 前端轮询读取。

## DTO、Entity、Service 分别什么时候需要？

- `dto/`：接收外部请求时校验参数，如问题长度、ID 和问答模式。
- `entities/`：定义数据库表；实体也可能集中在 persistence，例如检索记录和摘要缓存。
- `*.controller.ts`：HTTP 接口入口；`*.service.ts`：业务处理；`*.module.ts`：注册依赖并导出能力。
- `*.types.ts`、interface：内部数据约定，不会自动进行运行时请求校验。
- RAG 复用 chat/dto 的请求校验，并通过 persistence 保存检索记录，因此无需为凑目录创建 DTO 或 Entity。

## 推荐阅读顺序

先看入口 main.ts、bootstrap.ts、app.module.ts；再看问答调用链，接着看上传索引调用链，最后读任务恢复、存储实现和数据库迁移。关键逻辑的行内中文注释解释了版本切换、并发控制、失败降级和上下文预算。
