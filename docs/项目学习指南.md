# 多知识库文档问答项目学习指南

## 1. 项目解决什么问题

用户上传 PDF 或 Markdown，后台将正文解析、切片并建立索引。提问时先找到与问题有关的原文，再交给语言模型生成答案，并让引用编号对应原文。

这就是 RAG：检索增强生成。它不训练模型，也不是把所有文档每次全部发送给模型。回答质量取决于解析、切片、检索、证据组织和模型生成等多个环节。

本项目支持多个用户、多个知识库；一个知识库可以有多个聊天，一个聊天绑定一个知识库。聊天的问答来源与右侧工作台的来源分别选择。

## 2. 技术栈及职责

| 技术 | 在项目中的用途 |
| --- | --- |
| Vue 3、TypeScript、Vite | 前端页面、状态管理、开发代理及生产构建 |
| Element Plus、SCSS | 控件和深色界面样式 |
| NestJS、TypeScript | 模块化 API、鉴权、上传、检索及后台任务业务 |
| MySQL、TypeORM | 用户、知识库、文档版本、片段、任务、聊天和引用持久化 |
| 本地原件目录 | 保存上传文件，支持重新解析和重建索引 |
| Qdrant | 保存向量，按权限与生效版本过滤后进行相似度检索 |
| Redis、BullMQ | 后台任务队列、调度、重试与独立 Worker |
| 百炼 Embedding API | 默认 qwen3.7-text-embedding-flash，生成 1024 维向量 |
| 百炼 Rerank API | 默认 qwen3.7-text-rerank，对候选片段进行相关性排序 |
| 聊天模型 API | 查询规划、通用回答、文档回答、章节总结等 |
| SSE | 将阶段状态、正文、引用和结束事件逐步发送给前端 |

API 和 Worker 是分别启动的进程，共用业务代码、数据库、Redis、Qdrant 与原件目录。仅启动 API，后台文档处理可能一直排队。

## 3. 数据如何组织

核心关系可以理解为：

```text
用户 → 知识库 → 分类、文档
文档 → 原件版本 → 索引版本 → 原文片段
知识库 → 聊天 → 消息 → 引用快照
任务 → 记录处理阶段、数量、结果和失败原因
```

原件版本记录某次上传的文件与正文；索引版本记录该正文使用什么模型、维度、分词配置和切片规则处理。两者分开后，同一原件可以重建新的索引。

文档有当前生效索引和目标索引。新索引未完成前，问答继续使用旧索引；新结果全部就绪后才切换。模型名相同维度不同，或维度相同模型不同，都不能直接混用向量空间。

## 4. 上传到索引的流程

1. 前端普通上传或分片上传；分片会话绑定用户、知识库和目标文档。
2. 服务端保存原件、计算 SHA-256，并写入文档版本与任务记录。
3. API 返回任务编号，前端轮询处理进度。
4. 分发器将数据库中的待处理任务投递到 BullMQ；队列暂时不可用时可补投。
5. Worker 解析文本 PDF 或 Markdown，保存页码、标题路径和字符位置等可获得的信息。
6. 切片器建立父子片段。短片段用于检索，父段落用于补充上下文；默认子片段预算 384、重叠 64、父段落 1536。
7. 计算词频信息，调用 Embedding API，再把向量和标识 payload 写入 Qdrant。
8. 检查任务与目标版本仍有效，成功后发布生效索引。

当前默认 `estimate:utf8-v1` 按 UTF-8 字节数保守估算预算，因此上述数值不代表精确模型 token 数。可换成已核实匹配的本地 tokenizer。估算会让中文文本更早切片，但不应伪装成真实计费 token 数。

## 5. 一次提问如何得到答案

### 先决定是否需要文档

简单问候通过严格匹配直接回复。手动选择“通用回答”时，直接调用聊天模型，不检索原文、不生成文档引用。

“自动判断”复用查询规划模型，结合问题、最近对话和可用文件生成结构化计划。无明确文件选择时，可将独立通用问题路由到通用回答；选定文档或明确文档模式时优先执行文档问答。规划失败采用保守回退，不把检索错误悄悄变成通用答案。

### 文档问答流程

```text
用户、知识库鉴权
  → 确定本次文件和生效索引版本
  → 原问题词项做 BM25；改写问题做向量检索
  → 合并去重，用 RRF 融合排名
  → Rerank 重排
  → 扩展父段落或必要邻段
  → 按上下文预算组织证据
  → 生成答案与引用
```

BM25 擅长查错误码、英文标识符和精确词语；向量检索擅长查同义表达。词频保存在 MySQL，服务端按索引版本缓存倒排结构。两路各最多取 40 个候选，使用 RRF（常数 60）融合，最多 50 个进入重排，默认保留前 8 个命中再扩展上下文。

权限过滤必须发生在取 TopK 之前：先取得当前用户、当前知识库、当前生效索引集合，再查询向量库。否则其他库的数据可能挤占候选名额，甚至产生越权风险。

重排失败时可降级到融合排名并记录原因；单路检索失败可以使用另一条，双路失败返回服务错误。未检索到足够证据，不等于文件中一定没有对应内容。

### 全文总结

短文档可以完整装入证据预算时直接处理。长文档通过独立 QA 队列分章节、分批总结，按索引版本缓存，再汇总并核对原文证据。部分章节失败必须说明覆盖不完整。页面关闭不取消后台任务，可通过历史会话恢复结果。

## 6. 引用和流式返回

模型接收编号证据，回答中的 `[1]` 对应一个原文来源。服务端移除无效编号，将最终答案与引用快照保存到消息；快照包含文件名、版本、片段、位置和正文，历史回答可继续查看当时依据。

前端点击正文引用编号打开原文弹层。底部重复引用列表已移除，但引用数据仍保存。

SSE 包括 `status`、`sources`、正文、`citations`、`done`、`error` 等事件；长任务返回 `accepted` 后转为任务轮询。前端通过缓冲区处理跨网络块的事件。`done` 用规范化最终答案替换临时文本，确保刷新后与历史一致。

等待时的单行圆点提示由真实阶段事件驱动。服务端发送保活帧，检测长时间无正文，并在断开时取消上游生成。聊天和查询规划对 Qwen 默认关闭隐藏思考，避免长时间只有等待状态。

## 7. 替换、删除和重建为什么复杂

- 替换失败保留旧版；连续替换只允许最后接受的目标版本发布。
- 删除先在 MySQL 禁止新检索，再异步清理向量和原件；Worker 批次执行及发布前检查有效性，避免删除后重新发布。
- 全库重建逐文档切换，失败文档继续保留旧版，父任务展示部分失败。
- 分类、重命名只改业务元数据，不需要重新计算向量。
- 历史引用保留快照；文档更新后旧摘要、闪卡和导图属于旧版本产物。

## 9. 如何运行和判断效果

先看根目录 README 的启动顺序，再看 `docs/rag-quality-deployment.md` 的模型配置。已有数据库执行 `schema:upgrade`，空库初始化使用 `migration:run`；应用启动不自动改表。不要覆盖已有 `.env` 或提交密钥。

先用一份公开、较短且结构清晰的文档，等状态“已就绪”后问事实、概览、追问和无答案问题，再点击引用核对原文。用两个知识库放相似主题但结论不同的资料，可以检查隔离效果。

程序测试通过只说明被测试的功能和约束通过，不代表回答准确率达到某个百分比。`docs/evaluation/accuracy` 保存评估文档与 60 道待独立人工复核题；这些 Markdown 是测试数据，应保留。真实模型效果还需要核对召回、答案要点、引用支持和拒答表现。

当前支持文本 PDF、Markdown；不包含扫描件 OCR、复杂表格结构恢复或多模态理解。提升质量时应先定位解析、召回、证据覆盖还是生成出了问题，再调整对应环节。
